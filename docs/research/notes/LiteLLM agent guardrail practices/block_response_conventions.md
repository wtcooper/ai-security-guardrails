# Block / refusal response conventions across model APIs, and how agent loops react (as of 2026-10-08)

Method note: provider behaviour was taken from official docs (fetched 2026-10-08) and from the official SDK type definitions on GitHub `main` (fetched the same day). The SDK types are the most precise source for enum values. Framework behaviour was read directly from source on `main`. Sources marked **[unofficial]** are community, mirror or vendor-blog sources. Sources marked **[snippet]** are search-result summaries whose pages were not fetched in full.

---

## Q1. OpenAI Chat Completions: `finish_reason: "content_filter"`, `refusal`, HTTP 400 policy errors, structured-output refusals

### Takeaway
OpenAI Chat Completions has three separate in-band block signals: `finish_reason: "content_filter"`, a `message.refusal` string, and an ordinary text refusal written by the model. It also has out-of-band HTTP 4xx errors. Known codes are `invalid_prompt`, `content_policy_violation`, `cyber_policy` and `bio_policy`, and Azure adds `content_filter`. The OpenAI SDK never retries a 400. Its `.parse()` helper raises an exception when `finish_reason` is `content_filter`.

### Cited Findings
- The `Choice.finish_reason` enum is `Literal["stop", "length", "tool_calls", "content_filter", "function_call"]`. The docstring defines `content_filter` as "if content was omitted due to a flag from our content filters". `function_call` is marked **deprecated**. — [openai-python `types/chat/chat_completion.py`](https://github.com/openai/openai-python/blob/main/src/openai/types/chat/chat_completion.py)
- `ChatCompletionMessage.refusal: Optional[str]` holds "The refusal message generated by the model". Streaming chunks carry `delta.refusal: Optional[str]` and `logprobs.refusal`. — [chat_completion_message.py](https://github.com/openai/openai-python/blob/main/src/openai/types/chat/chat_completion_message.py), [chat_completion_chunk.py](https://github.com/openai/openai-python/blob/main/src/openai/types/chat/chat_completion_chunk.py)
- Structured Outputs added the `refusal` field because "a refusal does not follow the schema you have supplied in response_format". Its purpose is to let you render the refusal separately and avoid deserialization errors. In the Responses API the same thing appears as `item.type == "refusal"`. — [OpenAI: Introducing Structured Outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/); [OpenAI Cookbook: Structured Outputs intro](https://developers.openai.com/cookbook/examples/structured_outputs_intro) **[snippet]**
- The SDK's `chat.completions.parse()` helper raises `LengthFinishReasonError` when `finish_reason == "length"`. It raises `ContentFilterFinishReasonError(completion=...)` when `finish_reason == "content_filter"`. The raw `create()` call does not raise. — [openai-python `lib/_parsing/_completions.py` L109-113](https://github.com/openai/openai-python/blob/main/src/openai/lib/_parsing/_completions.py)
- The SDK retries only on HTTP 408, 409, 429 and >=500. A non-standard `x-should-retry: true|false` response header overrides that and is obeyed first. A 400 is "Not retrying". — [openai-python `_base_client.py` `_should_retry`](https://github.com/openai/openai-python/blob/main/src/openai/_base_client.py)
- When OpenAI blocks an input, reasoning models return HTTP 400 with `code: "invalid_prompt"`, `type: "invalid_request_error"` and the message "Invalid prompt: your prompt was flagged as potentially violating our usage policy". Users report it on benign prompts, from o1-mini through "GPT-6 Astra". — [OpenAI Community: o1 invalid prompt](https://community.openai.com/t/o1-mini-preview-api-getting-prompt-violating-usage-policy-on-innocent-prompts/971067) **[unofficial]**; [OpenAI Community: GPT-6 Astra "hello" rejected](https://community.openai.com/t/gpt-6-astra-harmless-chinese-greeting-hello-is-incorrectly-rejected-as-an-invalid-prompt/1395442) **[unofficial]**
- Cybersecurity safeguards apply to GPT-5.3-Codex and newer models (GPT-5.4, GPT-5.5). When they trigger, "API requests will return an error with the error code `cyber_policy`". For streaming, these errors "may be returned in the midst of other streaming events". The doc does not give the HTTP status. Without per-user `safety_identifier` values, access may be revoked for the whole organization. — [OpenAI docs: Cybersecurity checks](https://developers.openai.com/api/docs/guides/safety-checks/cybersecurity)
- Inspect AI's OpenAI adapter keeps a list of OpenAI and Azure error codes that are really policy blocks. It treats each as a refusal: `invalid_prompt` ("seems to happen for o1/o3"), `content_policy_violation` ("seems to happen for vision"), `content_filter` ("seems to happen on azure"), `bio_policy`, `cyber_policy` ("seems to happen for 5.4"), and any `invalid_request_error` whose message contains "blocked". — [inspect_ai `model/_openai.py` `openai_refusal_model_output`](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/src/inspect_ai/model/_openai.py)
- A secondary source says that on a usage-policy request a GPT model does **not** error. It returns HTTP 200 with `finish_reason: "stop"` and a refusal the model wrote itself. — [apiyi FAQ: OpenAI content safety refusal](https://docs.apiyi.com/en/faq/openai-content-safety-refusal) **[unofficial, reseller docs]**

### Inferences
- Plain OpenAI (not Azure) rarely uses `finish_reason: "content_filter"` in practice. Its usual signals are (a) a model-written text refusal with `stop`, (b) `message.refusal` under structured outputs, and (c) 4xx `invalid_prompt` or `cyber_policy` / `bio_policy` errors. `content_filter` mostly comes from Azure and from gateways and providers that emulate OpenAI, such as LiteLLM's Bedrock mapping (see Q7).
- A gateway can send `x-should-retry: false` on a block it returns as 5xx, or as a status the SDK would otherwise retry, so that OpenAI and Anthropic Stainless SDKs do not retry it automatically.

### Gaps
- No fetched official OpenAI page gives the exact HTTP status and JSON envelope for `cyber_policy` / `bio_policy` on non-streaming Chat Completions. `platform.openai.com` and `help.openai.com` returned 403 to the fetcher.
- No official statement was found on when OpenAI itself sets `finish_reason: "content_filter"`.

## Q2. OpenAI Responses API: refusal content parts, `status: "incomplete"` + `incomplete_details.reason: "content_filter"`, streaming

### Takeaway
The Responses API reports an output block as `status: "incomplete"` with `incomplete_details.reason: "content_filter"`, carried on the `response.incomplete` terminal event when streaming. A model refusal is an output content part `{"type": "refusal", "refusal": "..."}` and streams as `response.refusal.delta` / `response.refusal.done`. Policy errors such as `cyber_policy` arrive as `response.failed` with `response.error.code`.

### Cited Findings
- `IncompleteDetails.reason: Optional[Literal["max_output_tokens", "max_messages", "content_filter", "steered"]]`. The values `steered` (stopped at a safe boundary after a WebSocket `response.steer`) and `max_messages` are recent additions. — [openai-python `types/responses/response.py`](https://github.com/openai/openai-python/blob/main/src/openai/types/responses/response.py)
- Refusal content part: `class ResponseOutputRefusal: refusal: str; type: Literal["refusal"]`. — [response_output_refusal.py](https://github.com/openai/openai-python/blob/main/src/openai/types/responses/response_output_refusal.py)
- Streaming refusal delta: `{"type": "response.refusal.delta", "item_id", "output_index", "content_index", "delta", "sequence_number"}`. — [response_refusal_delta_event.py](https://github.com/openai/openai-python/blob/main/src/openai/types/responses/response_refusal_delta_event.py)
- Codex treats a stream that ends with `response.incomplete` and reason `content_filter` as `ApiError::ContentFilter`. Its display string is "stream disconnected before completion: Incomplete response returned, reason: content_filter". — [codex `protocol/src/error.rs`](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/error.rs); [codex `codex-api/src/error.rs`](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/error.rs)
- Codex maps the policy codes in `response.failed` events like this:
  - `cyber_policy` maps to `ApiError::CyberPolicy`, with the fallback message "This request has been flagged for possible cybersecurity risk."
  - `bio_policy` has the fallback "This content was flagged for possible biological risk."
  - `misalignment_policy_violation` has "This request was blocked due to a misalignment policy violation."
  - `invalid_prompt` maps to `InvalidPrompt`.
  - A Codex unit test feeds `{"type":"response.failed",...,"response":{...,"status":"failed",...,"error":{"code":"cyber_policy",...}}}` and expects the error to be fatal.

  — [codex `codex-api/src/sse/responses_error.rs`](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/sse/responses_error.rs); [codex `sse/responses.rs` test `cyber_policy_error_is_fatal`](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/sse/responses.rs)
- Example `response.incomplete` terminal event from a Codex bug report, shown with reason `max_output_tokens`. The `content_filter` variant has the same shape: `{"type":"response.incomplete","response":{"status":"incomplete","incomplete_details":{"reason":"max_output_tokens"},"usage":{...}}}`. — [openai/codex#38831](https://github.com/openai/codex/issues/38831)
- Inspect AI notes that when streaming, "the server returns HTTP 200 and then delivers safeguard blocks as an error event in the stream body". The OpenAI SDK then raises a plain `APIError` with no status, or the Responses stream yields an `error` event. — [inspect_ai `model/_openai.py` `openai_handle_stream_error`](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/src/inspect_ai/model/_openai.py)
- A community thread reports Responses API + Deep Research + MCP ending with `status: incomplete` and reason `content_filter`. — [OpenAI Community thread](https://community.openai.com/t/responses-api-with-deep-research-with-mcp-tool-failed-with-content-filter-issue/1377006) **[unofficial, snippet]**

### Inferences
- The Responses API has two kinds of "blocked" outcome. A **semantic terminal state** (200, `incomplete` + `content_filter`) means output was filtered. A **failed response** (`status: "failed"` + `error.code`) is used for account- or policy-level safeguards such as `cyber_policy`. Agent clients treat them differently (see Q7: Codex retries the first and stops on the second).

### Gaps
- Official OpenAI Responses API docs (platform.openai.com) could not be fetched, so there is no official wording on when `content_filter` vs. a `refusal` part is used. The enum values above come from the official SDK.

## Q3. Azure OpenAI / Foundry: `content_filter`, `content_filter_results`, HTTP 400 for prompts, Prompt Shields annotations, streaming / async filter

### Takeaway
Azure uses a split convention. A blocked **prompt** gets **HTTP 400** with `error.code: "content_filter"` (with `innererror.code: "ResponsibleAIPolicyViolation"`). A blocked **completion** gets **HTTP 200** with `finish_reason: "content_filter"`, usually with empty content. Annotations (`prompt_filter_results`, `content_filter_results`, including `jailbreak` and `indirect_attack` with `{detected, filtered}`) are attached either way. In Asynchronous Filter streaming mode, content can reach the client before the block signal, which is guaranteed within about 1,000 characters.

### Cited Findings
- The doc summarises the behaviour as follows. "Prompts that are classified at a filtered category and severity level return an HTTP 400 error." "Non-streaming completions calls don't return any content when the content is filtered. The `finish_reason` value is set to `content_filter`. In rare cases with longer responses, a partial result can be returned." With `n>1`, only the filtered choices carry `content_filter`. — [Microsoft Learn: Content filtering (Foundry classic), updated 2026-09-08](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-filter)
- Example HTTP 400 body for a prompt block: `{"error":{"message":"The response was filtered","type":null,"param":"prompt","code":"content_filter","status":400}}`. The doc's guidance is to "Modify the prompt and try again." — [same](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-filter)
- If the filter system is unavailable, the request still completes **unfiltered** with HTTP 200. `content_filter_results` then contains `{"error":{"code":"content_filter_error","message":"The contents are not filtered"}}`. — [same](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-filter)
- Microsoft's sample code reads the 400 details as `e.error.code == "content_filter" and e.error.innererror` and then `e.error.innererror.content_filter_results`. — [Microsoft Learn: Guardrail annotations](https://learn.microsoft.com/en-us/azure/ai-services/openai/concepts/content-filter-annotations)
- A Microsoft Q&A thread shows the inner error as `innererror: {code: "ResponsibleAIPolicyViolation", content_filter_result: {hate:{filtered,severity}, jailbreak:{detected, filtered}, ...}}`, using the singular `content_filter_result`. — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/2044545/content-filter-and-policy-violation-issues-when-us) **[semi-official, snippet]**
- Annotation shape on 200 responses:
  - `prompt_filter_results: [{prompt_index, content_filter_results: {hate:{filtered,severity}, jailbreak:{detected,filtered}, profanity:{detected,filtered}, self_harm, sexual, violence}}]`.
  - Each choice has `content_filter_results` with `protected_material_code:{citation:{URL,license},detected,filtered}`, `protected_material_text:{detected,filtered}`, and similar fields.
  - Optional models report `{detected, filtered}`. PII adds `redacted`. Groundedness is annotate-only, with offsets. Task adherence reports `{detected, filtered}`.

  — [Guardrail annotations](https://learn.microsoft.com/en-us/azure/ai-services/openai/concepts/content-filter-annotations)
- Indirect-attack (`indirect_attack`) annotations are listed for API versions 2024-04-01-preview and 2025-01-01-preview, and they require document delimiters in the prompt. Prompt Shields, protected material and similar filters can be set to "Annotate only" (flag without blocking) or to block. — [Guardrail annotations](https://learn.microsoft.com/en-us/azure/ai-services/openai/concepts/content-filter-annotations); [Content filtering](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-filter)
- Streaming in default mode buffers output, filters each chunk, and "it is immediately blocked and a guardrail error is returned instead". In **Asynchronous Filter** mode, tokens stream with no buffering. "The content filtering error signal is delayed... returned as soon as it's available, and the stream stops", and it is "guaranteed within a ~1,000-character window". The final block chunk has an empty `id` and looks like this: `{"id":"","object":"","created":0,"model":"","choices":[{"index":0,"finish_reason":"content_filter","content_filter_results":{"protected_material_text":{"detected":true,"filtered":true}},"content_filter_offsets":{"check_offset":65,"start_offset":65,"end_offset":1056}}],"usage":null}`, followed by `data: [DONE]`. Async mode requires API version 2024-02-01 or later. — [Microsoft Learn: Content streaming (updated 2026-09-08)](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-streaming)
- Billing: "Status 400 (prompt filtered): Charged for prompt evaluation". "Status 200 with finish_reason: 'content_filter': Charged for both prompt and completion tokens generated before filtering". — [Content streaming](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-streaming)
- Microsoft's best-practice list is: "Always check the `finish_reason`", and confirm there is no `error` object in `content_filter_results`. — [Content filtering](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-filter)
- **Deprecation flags:** the scenario examples use legacy `text_completion` objects (`davinci`/`ada`), and the pages are labelled "Foundry (classic)". The OpenAI Python 0.28.1 sample is marked deprecated. — [Content filtering](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-filter); [Guardrail annotations](https://learn.microsoft.com/en-us/azure/ai-services/openai/concepts/content-filter-annotations)

### Inferences
- Azure's prompt-block 400 is the main reason that OpenAI-compatible agent loops abort on "guardrail" events: the SDK raises `BadRequestError`, which is not retried (Q1). Its output-block 200 + `content_filter` does not abort the loop by itself, but some clients turn it into an exception (Q7: LangChain `AzureChatOpenAI`).

### Gaps
- No fetched Microsoft page settles whether the 400 inner object is `content_filter_result` or `content_filter_results`. The sample code and the Q&A thread disagree.
- Azure's Responses API filter behaviour (an `incomplete` / `content_filter` equivalent) was not checked.

## Q4. Anthropic Messages API: `stop_reason: "refusal"`, `stop_details`, streaming, other block signals

### Takeaway
Anthropic classifier blocks are **in-band HTTP 200** responses with `stop_reason: "refusal"` and a structured `stop_details: {type: "refusal", category, explanation}`. The refusal can come before any output (empty `content`) or mid-stream after partial text. Anthropic's guidance is that refusals "are responses, not errors". Clients should discard partial output and reset or alter context, or fall back to another model (server-side `fallbacks`, beta). The API still uses **400 errors** for "API input and copyright validation", and models can also refuse in plain text.

### Cited Findings
- "Starting with Claude 4 models, streaming responses from Claude's API return `stop_reason`: `"refusal"` when streaming classifiers intervene to handle potential policy violations." — [Anthropic: Handle streaming refusals](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/handle-streaming-refusals)
- `StopReason = Literal["end_turn","max_tokens","stop_sequence","tool_use","pause_turn","refusal","model_context_window_exceeded"]`. The docstring says `"refusal"` is "when streaming classifiers intervene to handle potential policy violations". — [anthropic-sdk-python `types/stop_reason.py`](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/types/stop_reason.py); [types/message.py](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/types/message.py)
- `Message.stop_details: Optional[RefusalStopDetails]` is `{type: Literal["refusal"], category: Optional[Literal["cyber","bio","frontier_llm","reasoning_extraction","general_harms"]], explanation: Optional[str]}`. It is `null` for every other stop reason. — [anthropic-sdk-python `types/refusal_stop_details.py`](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/types/refusal_stop_details.py)
- Example refusal: `{"id":"msg_...","type":"message","role":"assistant","model":"claude-fable-5","content":[],"stop_reason":"refusal","stop_details":{"type":"refusal","category":"cyber","explanation":"This request was declined because it could enable cyber harm."},"usage":{"input_tokens":412,"output_tokens":0}}`. The `explanation` text "is not stable, so display it rather than parse it". `category` and `explanation` can both be `null`, and that is a normal permanent value. — [Anthropic: Refusals and fallback](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback)
- **Conflict:** a WebFetch summary of the "Handling stop reasons" page reported `stop_details: {"type": "policy_violation", "policy": ...}`. The SDK types and two other official pages say `type: "refusal"` with `category` and `explanation`. The summary was most likely a fetch-summarizer error, so treat `type: "refusal"` as authoritative. — [Handling stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons) vs. [refusal_stop_details.py](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/types/refusal_stop_details.py)
- Streaming: `stop_reason` is `null` in `message_start`. It arrives in `message_delta`, and "`stop_details` arrives on the `message_delta` event alongside `stop_reason`". The example streamed refusal has partial content (`"text":"Hello.."`) followed by `stop_reason: "refusal"`. — [Handle streaming refusals](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/handle-streaming-refusals)
- "A refusal can arrive before any output, or mid-stream after partial output. In either case, treat any partial output as incomplete and discard it." — [Refusals and fallback](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback)
- Context guidance: "When you receive `stop_reason`: `refusal`, you must reset the conversation context before continuing... Attempting to continue without resetting will result in continued refusals." Also: "Re-sending a refused request to the same model usually results in another refusal." — [Handle streaming refusals](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/handle-streaming-refusals)
- Anthropic lists three refusal types: streaming classifier refusals (`stop_reason: refusal`), "API input and copyright validation" (400 error codes), and "Model-generated refusals" (standard text responses). — [Handle streaming refusals](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/handle-streaming-refusals)
- Migration notes:
  - "Refusals are responses, not errors... monitoring built only on error rates won't surface it."
  - Batch refusals are returned as **succeeded** results with `stop_reason: "refusal"`.
  - "The API continues to consolidate refusal handling around `stop_reason`: `"refusal"`."

  — [Handle streaming refusals](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/handle-streaming-refusals)
- Fallback (beta): `fallbacks: "default"` with header `anthropic-beta: server-side-fallback-2026-07-01` retries a declined request on a recommended model. A `{"type":"fallback","from":{"model":...},"to":{"model":...}}` content block marks the handoff. Mid-stream, "the open content block closes" and the fallback model continues from the partial `text`. The API applies "sticky routing" to later turns of that conversation. SDK middleware is also available (`BetaRefusalFallbackMiddleware`, and equivalents in other languages). The models listed are Claude Fable 5.1/5, Opus 5.5/5, Sonnet 5.5 and Haiku 5.5. — [Refusals and fallback](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback)
- Billing: a refusal before any output is billed only for categories `bio`, `frontier_llm` and `reasoning_extraction` ("as of September 2026"). A mid-stream refusal bills input tokens plus the output already streamed. Refusals still count against rate limits. — [Refusals and fallback](https://platform.claude.com/docs/en/build-with-claude/refusals-and-fallback)
- The Anthropic SDK retry policy matches OpenAI's: it obeys `x-should-retry`, and retries 408, 409, 429 and 5xx. — [anthropic-sdk-python `_base_client.py`](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/_base_client.py)

### Inferences
- `stop_reason: "refusal"` is now the most fully specified in-band block signal: it has a typed category, a stable location in the stream (`message_delta`), defined partial-output semantics, and a defined recovery (discard, reset, or fall back). A gateway that emits Anthropic format can reuse it directly.
- Claude 4 launched in May 2025. That date is from background knowledge and was not confirmed in a fetched source.

### Gaps
- No fetched source gives the date `stop_details` was added. The migration notes imply it came after the original `refusal` launch.
- The exact 400 error `type` / `message` for Anthropic "input and copyright validation" blocks was not captured.

## Q5. AWS Bedrock (Converse / InvokeModel) with Guardrails

### Takeaway
Bedrock Guardrails always block **in-band with HTTP 200**. Converse returns `stopReason: "guardrail_intervened"` and puts the configured blocked messaging in place of the model output as a normal assistant message. InvokeModel returns `"amazon-bedrock-guardrailAction": "INTERVENED" | "NONE"` in the body. An optional trace explains which policy fired.

### Cited Findings
- On a Converse block: "The `stopReason` field in the response is set to `guardrail_intervened`". The trace is in `trace` (or in the `metadata` event for ConverseStream). "The blocked content text that you have configured in the guardrail is returned in the `output` field. With `ConverseStream` the blocked content text is in the streamed message." — [AWS: Include a guardrail with the Converse API](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-converse-api.html)
- Example (input block): `{"output":{"message":{"role":"assistant","content":[{"text":"Sorry, I can't answer questions about heavy metal music."}]}},"stopReason":"guardrail_intervened","usage":{"inputTokens":0,"outputTokens":0,"totalTokens":0},"trace":{"guardrail":{"inputAssessment":{"<guardrailId>":{"topicPolicy":{"topics":[{"name":"Heavy metal","type":"DENY","action":"BLOCKED"}]},...}}}}}`. — [same](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-converse-api.html)
- When tools are used, guardrails do **not** evaluate `toolResult` content, tool definitions, or `toolUse.input` arguments. They evaluate only text and `guardContent`. — [same](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-converse-api.html)
- InvokeModel returns `HTTP/1.1 200` with `{<model fields>, "amazon-bedrock-guardrailAction": "INTERVENED | NONE", "amazon-bedrock-trace": {"guardrail": {...}}}`. InvokeModelWithResponseStream chunks carry the same fields, and "trace is returned only for the last chunk". — [AWS: Test your guardrail](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-test.html)
- Streaming modes: synchronous (the default) buffers and scans chunks before sending. In asynchronous mode (`streamProcessingMode: "ASYNCHRONOUS"`), chunks are sent immediately and "as soon as inappropriate content is identified, subsequent chunks will be blocked". Masking is not supported in async mode. — [AWS: Configure streaming response behavior](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-streaming.html)
- New: the `InvokeGuardrailChecks` API is **detect-only**. It returns 0-1 scores per check and "doesn't block, pass, or redact content". It is positioned for per-step checks in agentic loops. — [AWS: InvokeGuardrailChecks](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-invoke-guardrail-checks.html)

### Inferences
- Bedrock's design (200 + a normal assistant message + a distinct stop reason) lets a naive agent loop treat the block as a final answer and end gracefully. A guardrail-aware client can still branch on `stopReason`.

### Gaps
- No primary source was found that documents an HTTP error path for Converse guardrail blocks. Every documented path is 200.

## Q6. Google Gemini API / Vertex AI

### Takeaway
Gemini blocks in-band with HTTP 200. A blocked **prompt** returns **no candidates** plus `promptFeedback.blockReason`. A blocked **output** returns a candidate whose `finishReason` is `SAFETY`, `PROHIBITED_CONTENT`, `BLOCKLIST`, `SPII`, `RECITATION`, `IMAGE_SAFETY`, `IMAGE_PROHIBITED_CONTENT` or `IMAGE_RECITATION`, often with empty content, along with `safetyRatings`. Vertex adds `blockReason` values `MODEL_ARMOR` and `JAILBREAK`.

### Cited Findings
- `FinishReason` values: `FINISH_REASON_UNSPECIFIED, STOP, MAX_TOKENS, SAFETY, RECITATION, LANGUAGE, OTHER, BLOCKLIST, PROHIBITED_CONTENT, SPII, MALFORMED_FUNCTION_CALL, IMAGE_SAFETY, UNEXPECTED_TOOL_CALL, TOO_MANY_TOOL_CALLS, IMAGE_PROHIBITED_CONTENT, NO_IMAGE, IMAGE_RECITATION, IMAGE_OTHER, CONTINUATION`. For `SAFETY` the doc notes "When streaming, [content][] is empty if content filters blocks the output." — [google-genai python `types.py` `FinishReason`](https://github.com/googleapis/python-genai/blob/main/google/genai/types.py)
- `BlockedReason` (for `promptFeedback.blockReason`) values: `BLOCKED_REASON_UNSPECIFIED, SAFETY, OTHER, BLOCKLIST, PROHIBITED_CONTENT, IMAGE_SAFETY, MODEL_ARMOR` ("not supported in Gemini API") and `JAILBREAK` ("blocked as a jailbreak attempt. Both of the last two are Vertex-only. — [google-genai `types.py` `BlockedReason`](https://github.com/googleapis/python-genai/blob/main/google/genai/types.py)
- The Gemini API "Returns either all requested candidates or none of them. Returns no candidates at all only if there was something wrong with the prompt (check `promptFeedback`)". `PromptFeedback` holds `blockReason` and `safetyRatings[]`. — [Gemini API reference: generateContent](https://ai.google.dev/api/generate-content)

### Inferences
- A prompt block that has **zero candidates** is the Gemini case most likely to crash naive clients, which index `candidates[0]`. A gateway emulating Gemini format should return at least one candidate with a `finishReason` if it wants agents to keep going.

### Gaps
- The Vertex "Configure content filters / Process blocked responses" pages could not be extracted (the fetcher returned only the navigation index). Vertex HTTP status for blocks is therefore unverified from Vertex docs. It is presumed 200, based on the Gemini API description.

## Q7. How agent frameworks and clients treat these signals

### Takeaway
No two frameworks behave the same way.
- **HTTP 400s** are never auto-retried by the OpenAI or Anthropic SDKs, and they propagate as exceptions that end agent runs, unless the framework converts them. Inspect AI converts them.
- **In-band blocks** (200 + `content_filter` / `refusal`) used to be treated as empty or normal turns, which caused silent empty outputs or retry loops. They are now increasingly surfaced explicitly:
  - OpenAI Agents SDK 0.15: `ModelRefusalError`
  - Vercel AI SDK: unified `content-filter`
  - Inspect: `stop_reason="content_filter"`
  - Codex: retries with a developer guidance message
- Some clients still turn in-band blocks into hard errors: LangChain `AzureChatOpenAI`, OpenAI `.parse()`, and Claude Code's "API Error" message.

### Cited Findings

**OpenAI Python SDK**
- 400 is not retried. Only 408, 409, 429 and >=500 are retried, unless `x-should-retry` says otherwise. `.parse()` raises `ContentFilterFinishReasonError` when `finish_reason == "content_filter"`. — [openai-python `_base_client.py`](https://github.com/openai/openai-python/blob/main/src/openai/_base_client.py); [`_completions.py`](https://github.com/openai/openai-python/blob/main/src/openai/lib/_parsing/_completions.py)

**OpenAI Agents SDK (openai-agents-python)**

### Inferences
- **HTTP 400 / 403 / 446 blocks:** every SDK examined (OpenAI, Anthropic, and Vercel via `APICallError`) raises an exception and does not retry. Agent loops in the OpenAI Agents SDK, LangGraph, CrewAI and Claude Agent SDK therefore **abort the run** unless the user adds handling. Inspect is the exception: it turns known 400 policy codes into a `content_filter` output.
- **200 + `finish_reason: "content_filter"` with non-empty assistant text:**
  - Ends the loop gracefully in the Vercel AI SDK, AutoGen, the Agents SDK (treated as a normal final message because content is non-empty), and plain `ChatOpenAI`.
  - Raises in `AzureChatOpenAI` and in OpenAI `.parse()`.
  - Retried in Inspect `react(retry_refusals>0)` and in Codex (Responses `incomplete`).
- **200 + empty content + `content_filter`:** becomes `ModelRefusalError` in the Agents SDK (≥0.15).
- **200 + `stop` + explanatory text:** the most universally non-breaking option, but no client can tell it from a real answer. The agent may then retry the task by another route, which is the behaviour Codex's guidance text explicitly tries to suppress.
- **Anthropic-format `stop_reason: "refusal"`:** Claude Code treats it as a turn-ending "API Error". By Anthropic's own docs, a context that keeps the refused turn will keep refusing. That explains the reported session contamination. A gateway emitting `refusal` to Claude Code should expect the user to have to rewind or start a new session. The claim that Claude Code renders `stop_reason: "refusal"` as this message is an inference from issue text, because Claude Code's source is closed.

- CrewAI: the source fetch of `lib/crewai/src/crewai/llm.py` found no `content_filter` or refusal handling. GitHub code search was rate-limited, so CrewAI's behaviour is unverified. Note that CrewAI routes through LiteLLM.
- The Vercel AI SDK `APICallError.isRetryable` status-code set and the OpenAI Agents SDK opt-in `ModelSettings.retry` policy were not verified from source.
- The LangGraph prebuilt agent has no specific handling that was verified. The abort-on-exception behaviour above is inferred from standard exception propagation.
- Claude Code's internal handling of `stop_details.category` and server-side fallback was not verifiable because the source is closed.

## Q8. Is there an emerging standard or consensus for gateways: in-band (200) refusal vs error response?

### Takeaway
There is **no formal standard**. Model providers are converging on **in-band 200** block signals: Anthropic (`refusal`, explicitly "responses, not errors"), Bedrock (`guardrail_intervened`), Gemini (`blockReason` / `finishReason`) and Azure output filtering (`content_filter`). The remaining errors are Azure prompt blocks (400) and OpenAI account-level safeguards (`invalid_prompt`, `cyber_policy`). Gateways still mostly **default to errors** (LiteLLM 400, Portkey 446, OpenRouter 403), but each offers or documents an in-band 200 option because errors break chat and agent flows.

### Cited Findings
- **LiteLLM:**
  - By default a blocking guardrail returns **HTTP 400**: `{"error":{"message":{"error":"Violated guardrail policy","bedrock_guardrail_response":{"action":"GUARDRAIL_INTERVENED",...}},"code":"400"}}`.
  - `disable_exception_on_block: true` returns **HTTP 200** with the guardrail's blocked message as assistant `content` and `finish_reason: "content_filter"`. The stated reason: "particularly useful when integrating with OpenWebUI, where exceptions can interrupt the chat flow".

  — [LiteLLM docs: Bedrock Guardrails](https://docs.litellm.ai/docs/proxy/guardrails/bedrock)
- LiteLLM is not consistent across guardrails: a docs PR states "DynamoAI guardrail block returns HTTP 500, not 400". — [BerriAI/litellm-docs PR #1814](https://github.com/BerriAI/litellm-docs/pull/1814) **[snippet]**
- **Portkey** (`/v1/decisions`): a hard deny returns **HTTP 446** with the standard guardrail error shape (`error` with message, type and `hook_results`). A soft deny (`deny: true` + `softDeny200: true`) returns **HTTP 200**, keeping "the response shape consistent with a normal decisions response". — [Portkey docs: Decisions guardrails](https://portkey.ai/docs/product/guardrails/decisions-guardrails)
- **OpenRouter:**
  - Moderation of the input gives **HTTP 403**: `{"error":{"code":403,"message":"Request blocked","metadata":{"reasons":[...],"flagged_input":"...","provider_name":"...","model_slug":"..."}}}`.
  - A mid-stream filter gives HTTP **200** (headers already sent) and an SSE chunk `{"error":{"code":403,...,"metadata":{"error_type":"content_policy_violation"}},"choices":[{"finish_reason":"error"}]}`.

  — [OpenRouter: Errors and debugging](https://openrouter.ai/docs/api_reference/errors-and-debugging)
- MLflow AI Gateway guardrails: with the Block action, "callers receive an HTTP 400 with a structured error body containing the guardrail name and the rationale". — [MLflow blog: Gateway guardrails](https://mlflow.org/blog/gateway-guardrails/) **[snippet]**
- A vendor FAQ describes the OpenAI-compatibility rationale: "block actions return 400 guardrail_blocked and cost no quota, and are marked skip-retry since re-running the identical prompt blocks again". — [OrcaRouter Security FAQ](https://docs.orcarouter.ai/security/reference/faq) **[unofficial vendor, snippet]**
- Anthropic: "The API continues to consolidate refusal handling around `stop_reason`: `"refusal"`". "Refusals are responses, not errors." — [Anthropic: Handle streaming refusals](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/handle-streaming-refusals)
- Framework maintainers are standardizing on the in-band signal:
  - The Agents SDK synthesizes a refusal from bare `content_filter` specifically to handle "Anthropic on Amazon Bedrock via LiteLLM". — [openai-agents-python `chatcmpl_stream_handler.py`](https://github.com/openai/openai-agents-python/blob/main/src/agents/models/chatcmpl_stream_handler.py)
  - Inspect "Builds on the existing `StopReason` value `"content_filter"` rather than introducing a new signal". — [inspect_ai `design/fail-on-refusal.md`](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/design/fail-on-refusal.md)
  - Vercel unifies all provider block reasons to `content-filter`. — [vercel/ai mappers](https://github.com/vercel/ai/blob/main/packages/anthropic/src/map-anthropic-stop-reason.ts)
- Codex shows that an agent works best when the block signal comes with guidance. On `content_filter` it injects a developer message telling the model not to work around the block and to "Continue unrelated authorized work". — [codex `prompts/src/model_messages.rs`](https://github.com/openai/codex/blob/main/codex-rs/prompts/src/model_messages.rs)

### Inferences
**De facto in-band shapes a gateway can emit, per API surface**

| Surface | In-band block shape that clients understand | Known client reactions |
|---|---|---|
| OpenAI Chat Completions | 200; `choices[0].message.content` = short explanation; `finish_reason: "content_filter"`. Optionally `message.refusal` = the same text. | Vercel ends loop. AutoGen records it. Agents SDK: final output if content non-empty, `ModelRefusalError` if empty or `refusal` set. `AzureChatOpenAI` **raises**. `.parse()` **raises**. Inspect `react` may retry. |
| OpenAI Responses | 200; `status: "completed"` with an `output_text` explanation, **or** a `refusal` content part, **or** `status: "incomplete"` + `incomplete_details.reason: "content_filter"` | Agents SDK raises `ModelBehaviorError` on `incomplete`. Codex **retries** with guidance on `incomplete`/`content_filter` and stops on `failed`/`cyber_policy`. |
| Anthropic Messages | 200; `stop_reason: "refusal"`; `stop_details: {type:"refusal", category, explanation}`; content empty or partial | Vercel `content-filter`. Inspect `content_filter` (fallback-able). Claude Code: turn-ending "API Error", and the user must rewind or start a new session. |
| Bedrock Converse | 200; `stopReason: "guardrail_intervened"`; blocked messaging as assistant text | Vercel `content-filter`. Via LiteLLM it appears as `content_filter`, often with empty content. |
| Gemini | 200; `promptFeedback.blockReason` (no candidates) or `finishReason: SAFETY` etc. | Vercel `content-filter`. Zero-candidate responses risk index errors. |

**Choosing a format**
- For "keep the agent working", the evidence favours **200 in-band** blocks over 4xx: no 4xx is retried and every 4xx aborts unhandled loops. Within 200, the trade-off is machine-readability against compatibility:
  - `finish_reason: "content_filter"` (or Anthropic `refusal`) with **non-empty explanatory content** is detectable by guardrail-aware clients and ends the loop gracefully in most frameworks. Clients that convert it to an exception are known: LangChain Azure and OpenAI `.parse()`.
  - Empty content plus `content_filter` triggers refusal exceptions in Agents SDK ≥0.15.
  - `finish_reason: "stop"` with text is the safest for compatibility, but it is invisible to monitoring and may invite workaround attempts.
- Where the agent should **continue other work** rather than stop, the most effective documented pattern is Codex's. Signal the block and give the model explicit text: do not retry or work around the block, explain the limitation, continue unrelated work. A gateway could approximate this by putting such guidance in the blocked-message text it returns.
- A gateway that must return an error (for example on hard policy) should use a non-retryable status (400/403) or `x-should-retry: false`, so Stainless-generated SDKs and Codex do not hammer it with retries. Codex treats `invalid_prompt` and `cyber_policy` / `bio_policy` as fatal.

### Gaps
- No IETF, OpenAI-compatibility-spec or cross-vendor standards document on block signalling was found.
- No LiteLLM GitHub issue directly about agents breaking on guardrail 400s was found. The issue searches returned nothing relevant.
- The Portkey "246" status (soft-fail on the main gateway) was not confirmed. The decisions page lists only 446 and 200.
