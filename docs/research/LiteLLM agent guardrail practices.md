# Keep agents working: refuse in-band, cut surgically

*Research as of 2026-10-08, against LiteLLM v1.104.2 (latest stable) and the repo's pinned v1.103.2.*

LiteLLM has no "agent mode": an agent loop reaches the gateway as a series of ordinary model calls, so a guardrail sees each tool's output when the client sends it back in the next request (the `pre_call` hook) and each tool the model wants to run in the model's reply (the `post_call` hook), with three separate hooks that apply only when LiteLLM itself runs a tool over MCP. LiteLLM blocks with an HTTP error by default (400, or 500 if a custom guardrail raises a plain Python exception), but the evidence says a gateway that wants agents to keep working should use an **in-band refusal** instead: a normal HTTP 200 response whose content is a short refusal, marked `finish_reason: "content_filter"` on Chat Completions, because SDKs never retry a 400, agent frameworks abort the run on the exception it raises, and model providers themselves have moved to 200-status block signals. LiteLLM supports this through a public helper, `raise_passthrough_exception`, that its docs site never mentions. Our `agentic-security` guardrail already makes the choices the evidence favours on Chat Completions: 200 refusals, buffered streams so no tool call leaks, an in-place rewrite that keeps a blocked inference billed, and surgical withholding that cuts only the injected lines of a tool result and kept task success under attack at 56–58%, against 6% when the turn was refused and 20% when the whole result was withheld, an option most commercial gateways do not offer (they halt the agent). The weaknesses sit at the edges: when the judge's own provider safety-blocks a judge call the guard silently fails open, so the riskiest content gets through; Anthropic Messages and Responses API traffic (what Claude Code and Codex use) gets a thinner tool-call check, odd refusal shapes and probably unbilled post-call blocks; fail-opens and withholds are invisible in LiteLLM's own telemetry; and in long agent turns a cut tool result slides out of the 10-message window and reaches the model again uncut. Every fix fits the drop-in constraint of one Python file plus config, and four should land before production: treat provider safety blocks as flags, make the non-chat endpoints first-class, regression-test on the enterprise gateway's exact LiteLLM version, and make fail-opens visible.

## LiteLLM sees an agent loop as a series of separate model calls

LiteLLM releases weekly and maintains several patch lines at once. The latest stable release is **v1.104.2, published 2026-10-08**, and lines 1.101 through 1.104 all received patches on 2026-10-07 and 2026-10-08 ([PyPI](https://pypi.org/pypi/litellm/json); [GitHub releases](https://github.com/BerriAI/litellm/releases)). The repo pins 1.103.2, but a source diff shows **the guardrail framework is identical between the two apart from typing annotations**: `CustomGuardrail`, `apply_guardrail`, the guardrail exceptions and the hook list all match. The only guardrail-related additions in 1.104 are an opt-in `include_guardrail_response` field, which returns verdicts in non-streaming response bodies, and a new `/v1/decisions` route ([v1.104.2 notes](https://github.com/BerriAI/litellm/releases/tag/v1.104.2)). The docs moved out of the main repository into BerriAI/litellm-docs in April 2026 ([litellm-docs](https://github.com/BerriAI/litellm-docs)), and they contradict the code on two points that matter here, the default streaming behaviour and the status code of tool-permission blocks. Treat any code behaviour described below as something to re-check on the version the enterprise gateway actually runs.

LiteLLM has **no agent, tool-call or agent-to-agent guardrail mode**. It has eight hooks ([`GuardrailEventHooks`](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/types/guardrails.py#L1265)). In a client-side agent loop the client runs the tools, not the gateway, so the loop looks to the gateway like a run of independent model calls. A tool's output becomes visible only when the client sends it back as a `role: "tool"` message in the next request, at `pre_call`. A tool call, meaning the model asking to run a tool, is visible in the model's reply at `post_call`. The three MCP hooks apply only when LiteLLM itself executes a tool over MCP (Model Context Protocol, the standard protocol between agents and tool servers).

| Hook (`mode`) | When it runs | What a custom guardrail sees | What it can do |
|---|---|---|---|
| `pre_call` | Before the model | The whole conversation: every message including tool results, earlier tool calls, tool definitions | Rewrite the request, or block |
| `during_call` | In parallel with the model | Same input as `pre_call` | Block only; a block cancels the model call mid-flight, which we measured recorded as $0 |
| `post_call` | After the model | The new reply's text and tool calls only, not the conversation | Rewrite or block; on streams only if buffering is on |
| `logging_only` | Out of band | Logged input and output | Nothing the client sees |
| `pre_mcp_call` | Before LiteLLM runs an MCP tool, and on `tools/list` | Tool arguments; tool descriptions at discovery | Block, mask, or hide poisoned tools |
| `during_mcp_call` | Alongside an MCP call | Documented in one sentence | Unclear |
| `post_mcp_call` | After an MCP tool returns, before the model sees it | The tool result's text | Block (the model gets an MCP tool error) or mask |
| `realtime_input_transcription` | Realtime audio | Not relevant here | Not relevant here |

Sources: [Quick start](https://docs.litellm.ai/docs/proxy/guardrails/quick_start), [Custom guardrail](https://docs.litellm.ai/docs/proxy/guardrails/custom_guardrail), [MCP guardrails](https://docs.litellm.ai/docs/mcp_guardrail).

For custom logic, the documented path is to **subclass `CustomGuardrail` and implement one method, `apply_guardrail(inputs, request_data, input_type)`**. LiteLLM translates each API format (Chat Completions, Anthropic Messages, Responses, MCP, agent-to-agent) into a common `inputs` dict, passes it in, and writes back whatever the method returns; raising an exception blocks the call ([Custom guardrail](https://docs.litellm.ai/docs/proxy/guardrails/custom_guardrail)). On `pre_call`, `inputs` holds every message's text, earlier tool calls, the tool definitions, and `structured_messages`, the full conversation in OpenAI format. **There is no separate tool-results field**: tool results arrive inside `texts` and `structured_messages` ([`GenericGuardrailAPIInputs`](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/types/utils.py#L4493)). On `post_call` the guardrail gets only the new reply. A change to pass the conversation to `post_call` too was merged and reverted within two days in September 2026 ([PR #41986](https://github.com/BerriAI/litellm/pull/41986)), so a guardrail that needs context after the model has run must read the raw request itself. To rewrite content, a guardrail edits `texts` or `tool_calls` in place, or returns a new `structured_messages` list; in-place edits to that list are ignored.

LiteLLM's explicit setting for **indirect prompt injection**, meaning instructions hidden in data an agent reads, is `scan_only_tool_results`, added in v1.97.0 for "agent harnesses whose own prompt scaffolding is trusted but often trips prompt-attack detectors" ([types/guardrails.py](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/types/guardrails.py#L943)). Its two ways of limiting how much history a guardrail sees do not suit a drop-in: `experimental_use_latest_role_message_only` keeps only the latest message for each role, and `only_scan_new_messages` needs a per-session cache, which a guardrail with no state cannot use.

**Streaming is where the docs and the code disagree most.** The custom-guardrail page says a `post_call` guardrail on a stream runs only after every chunk has been delivered, so it can only audit, and the same page says built-in guardrails buffer. The code shows that `apply_guardrail` guardrails **by default scan a sample of one chunk in five, with buffering off**, except for Bedrock, Straiker and Rubrik ([unified_guardrail.py](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/proxy/guardrails/guardrail_hooks/unified_guardrail/unified_guardrail.py#L976)). Under sampling, early chunks, including the start of a tool call, can reach the client before any verdict. The fix is the `streaming_buffer_until_moderated` flag, which holds every chunk until the end-of-stream verdict. LiteLLM's OWASP page tells operators to set it "when a block must land before any chunk reaches the client" ([OWASP mapping](https://docs.litellm.ai/docs/proxy/security_owasp_llm_top10)), and the code reads it from any guardrail's attributes even though it is declared only as a Bedrock parameter. LiteLLM switches buffering off automatically when a guardrail masks responses, so on a stream a guardrail can rewrite output or block it before delivery, but not both.

LiteLLM has no single "guardrails for agents" page. Its guidance, spread across the OWASP LLM Top 10 mapping (checked against v1.104.0), the MCP page and the tool-control pages, comes to five recommendations. Scan tool results before the model sees them, with `post_mcp_call` or with `scan_only_tool_results` on `pre_call`. Scan tool descriptions at discovery so poisoned MCP tools are hidden. Set `default_on: true` on MCP guardrails, because MCP sub-calls do not inherit a request's guardrail selection. Restrict tools and arguments deterministically, with `tool_permission` regex rules and with Tool Policies, which reject a trusted tool once untrusted tool output is in the conversation. And remember that guardrails "are classifiers, so a crafted injection can pass any of them", so pair them with least privilege ([OWASP mapping](https://docs.litellm.ai/docs/proxy/security_owasp_llm_top10); [Tool Permission](https://docs.litellm.ai/docs/proxy/guardrails/tool_permission); [Tool Policies](https://docs.litellm.ai/docs/proxy/tool_policies)). Two things are missing. LiteLLM gives no guidance on how to report a blocked tool result back to an agent loop that runs on the client. And it has no consistent failure policy: each integration decides whether to fail open (let the request through when the guard cannot decide) or fail closed (block it). The generic `unreachable_fallback` setting defaults to fail-closed but only eight integrations implement it ([types/guardrails.py](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/types/guardrails.py#L1058)), while LiteLLM's own LLM-as-a-judge guardrail fails open on judge errors and blocks with **HTTP 422** ([LLM-as-a-Judge](https://docs.litellm.ai/docs/proxy/guardrails/llm_as_a_judge)).

## A 200 refusal keeps the loop alive; a 400 ends it

**LiteLLM's default block is an error.** Raising `HTTPException(400)` or `GuardrailRaisedException` returns an OpenAI-style error body with status 400, and nearly every vendor integration blocks this way, including Azure, Lakera, Model Armor, Prisma AIRS, Pangea and Lasso. A custom guardrail that raises a plain Python exception, as the docs' own example does, produces **HTTP 500** ([Custom guardrail](https://docs.litellm.ai/docs/proxy/guardrails/custom_guardrail); [common_request_processing.py](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/proxy/common_request_processing.py#L3735)). The status matters because of how SDKs retry: **the OpenAI and Anthropic SDKs automatically retry 408, 409, 429 and every 5xx, and never retry a 400** ([openai-python](https://github.com/openai/openai-python/blob/main/src/openai/_base_client.py); [anthropic-sdk-python](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/_base_client.py)). A 500 block therefore turns into repeated identical attempts, and a 400 surfaces in the client as an exception. Agent loops in the OpenAI Agents SDK, LangGraph and the Claude Agent SDK end the run on that exception unless the developer adds handling; this follows from how exceptions propagate, and we did not run those loops against a real 400. Inspect AI is the exception, converting known provider policy errors into a `content_filter` result ([inspect_ai](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/src/inspect_ai/model/_openai.py)).

LiteLLM also has a supported way to refuse in-band with HTTP 200. A guardrail calls `self.raise_passthrough_exception(...)`, which raises `ModifyResponseException`, and the proxy turns that into a 200 response ([custom_guardrail.py](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/integrations/custom_guardrail.py#L256); [exceptions.py](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/exceptions.py#L1201)). The helper is public, has a docstring, and is used by the Bedrock, Gray Swan, Straiker, Rubrik and Custom Code guardrails, but **the docs site never mentions it**, so it is supported code with no documented guarantee. Its output depends on the endpoint:

| Endpoint | What the in-band refusal looks like | Problem |
|---|---|---|
| Chat Completions | The refusal as assistant content, with `finish_reason: "content_filter"`; streamed as a text chunk followed by a final `content_filter` chunk ([proxy_server.py](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/proxy/proxy_server.py#L11746)) | None |
| Anthropic `/v1/messages` | A text block with `stop_reason: "end_turn"` ([anthropic endpoints](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/proxy/anthropic_endpoints/endpoints.py#L206)) | Looks exactly like a normal answer |
| Responses API | `status: "completed"` with one output item ([responses endpoints](https://github.com/BerriAI/litellm/blob/v1.104.2/litellm/proxy/response_api_endpoints/endpoints.py#L434)) | The item lacks `type: "message"` and uses `"text"` instead of `"output_text"`, so strict clients may fail to parse it |

LiteLLM's other built-in in-band options point the same way. Bedrock's `disable_exception_on_block` was added because "exceptions can interrupt the chat flow" in OpenWebUI ([Bedrock](https://docs.litellm.ai/docs/proxy/guardrails/bedrock)). Gray Swan has `on_flagged_action: passthrough`, the policy pipeline has a `modify_response` action ([Policy Flow Builder](https://docs.litellm.ai/docs/proxy/guardrails/policy_flow_builder)), and `tool_permission`'s `rewrite` strips or rewrites disallowed tool calls and returns 200 ([Tool Permission](https://docs.litellm.ai/docs/proxy/guardrails/tool_permission)). On the MCP path, a blocked tool result comes back to the model as an MCP tool error it can read and recover from ([MCP guardrails](https://docs.litellm.ai/docs/mcp_guardrail)).

**Model providers have converged on in-band blocks**, and that is the strongest argument for refusing in-band. Anthropic returns 200 with `stop_reason: "refusal"` and says plainly that "refusals are responses, not errors" ([Anthropic](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/handle-streaming-refusals)). Bedrock Converse returns 200 with `stopReason: "guardrail_intervened"` and the canned message as the assistant reply ([AWS](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-converse-api.html)). Gemini returns 200 with a block reason ([Gemini API](https://ai.google.dev/api/generate-content)), and Azure returns 200 with `finish_reason: "content_filter"` for filtered output ([Azure](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-filter)). The exceptions are errors: Azure blocks a filtered *prompt* with HTTP 400 `content_filter`, and OpenAI rejects some requests with `invalid_prompt` or `cyber_policy` errors ([OpenAI cyber checks](https://developers.openai.com/api/docs/guides/safety-checks/cybersecurity)). Agent frameworks have followed the providers. The Vercel AI SDK maps every provider's block signal to a single `content-filter` finish reason and ends its loop cleanly on it ([Vercel AI SDK](https://github.com/vercel/ai/blob/main/packages/ai/src/generate-text/generate-text.ts)), and the OpenAI Agents SDK turns a bare `content_filter` into a refusal, with a code comment naming "Anthropic on Amazon Bedrock via LiteLLM" as the reason ([Agents SDK](https://github.com/openai/openai-agents-python/blob/main/src/agents/models/chatcmpl_stream_handler.py)). Gateways still default to errors (Portkey 446, OpenRouter 403, Kong 400 or 403, Azure API Management 403, Cloudflare error codes 2016 and 2017), but Portkey, for one, also documents a 200 path: status 246 means "flag and continue", and `softDeny200` turns a block into a 200 ([Portkey](https://portkey.ai/docs/product/guardrails); [OpenRouter](https://openrouter.ai/docs/api_reference/errors-and-debugging)).

| API the agent speaks | Provider's own block signal | Clients that still break | Best gateway shape |
|---|---|---|---|
| OpenAI Chat Completions | `finish_reason: "content_filter"`, `message.refusal`, or a 400 error | LangChain `AzureChatOpenAI` raises `ValueError`; the OpenAI SDK's `.parse()` raises; Agents SDK 0.15+ raises `ModelRefusalError` if content is empty or `refusal` is set | 200, non-empty refusal text, `content_filter`, no tool calls, `refusal` unset |
| OpenAI Responses | `status: "incomplete"` with `content_filter`; a `refusal` content part; `response.failed` with `cyber_policy` | Agents SDK raises on `incomplete`; Codex retries `incomplete` with guidance and stops on `failed` | 200, `completed`, with a well-formed `message` item containing `output_text` |
| Anthropic Messages | 200, `stop_reason: "refusal"`, `stop_details` with a category | Claude Code shows `refusal` as an "API Error", and users report the session staying blocked afterwards | `end_turn` text for compatibility; `refusal` only once clients are tested |
| Bedrock Converse | 200, `guardrail_intervened`, canned text | Through LiteLLM it often arrives as `content_filter` with empty content | Clients reach us in OpenAI or Anthropic format |
| Gemini | 200; a blocked prompt returns zero candidates | Code that reads `candidates[0]` crashes | Always return at least one candidate |
| Azure (as upstream) | Prompt: 400 `content_filter`; output: 200 `content_filter` | Any client, on the prompt 400 | Outside our guard; upstream prompt blocks still abort agents |

Sources: [LangChain azure.py](https://github.com/langchain-ai/langchain/blob/master/libs/partners/openai/langchain_openai/chat_models/azure.py); [openai-python parsing](https://github.com/openai/openai-python/blob/main/src/openai/lib/_parsing/_completions.py); [Agents SDK release notes](https://github.com/openai/openai-agents-python/blob/main/docs/release.md); [Agents SDK Responses model](https://github.com/openai/openai-agents-python/blob/main/src/agents/models/openai_responses.py); [Codex error.rs](https://github.com/openai/codex/blob/main/codex-rs/protocol/src/error.rs); [Claude Code #63751](https://github.com/anthropics/claude-code/issues/63751); [google-genai types](https://github.com/googleapis/python-genai/blob/main/google/genai/types.py).

Three details decide whether an in-band refusal keeps an agent working. The first is to **keep the refusal text non-empty and leave `message.refusal` unset**, because the OpenAI Agents SDK treats a `content_filter` reply that has text as a normal final answer and raises only when the content is empty or the `refusal` field is set. The second is to **know which clients still throw**: an Azure-heavy enterprise should test `AzureChatOpenAI` and `.parse()` specifically. The third is to **tell the agent what to do next**. When a content filter blocks a response, Codex injects a developer message telling the model not to work around the block "through repeated attempts, altered formatting, splitting, encoding, tools, subagents", to explain the limitation, and to "continue unrelated authorized work" ([Codex model_messages.rs](https://github.com/openai/codex/blob/main/codex-rs/prompts/src/model_messages.rs)). A refusal that only says the request "was not completed" gives the next turn nothing to act on, and a refusal sent with `finish_reason: "stop"` is invisible to monitoring and invites the agent to try another route.

**On streams, decide before the first byte.** Once the 200 status and some chunks have gone out, a gateway can only block with a terminating chunk or an error frame inside the stream, and clients handle those inconsistently: OpenRouter sends an error object with `finish_reason: "error"`, LiteLLM turns an exception mid-stream into an SSE error frame (SSE, server-sent events, is the streaming wire format), and Azure API Management stops forwarding without any error ([APIM](https://learn.microsoft.com/en-us/azure/api-management/llm-content-safety-policy)). Providers that stream before deciding accept that some content leaks first; Azure's asynchronous filter, for example, guarantees a block only within about 1,000 characters ([Azure streaming](https://learn.microsoft.com/en-us/azure/ai-foundry/openai/concepts/content-streaming)). A guardrail that must stop a tool call cannot accept that, so the right pattern is to buffer the whole reply and end the stream with a normal `content_filter` final chunk. When a block has to be an error, for a hard policy or a client that requires one, use a non-retryable status (400 or 403), send `x-should-retry: false` on any status the SDKs would otherwise retry, and keep the reason out of the response body so an attacker cannot use the guard as an oracle, as Kong's Lakera plugin does by hiding detection categories by default ([Kong Lakera](https://developer.konghq.com/plugins/ai-lakera-guard/)).

## Vendors halt on injected tool output; research favours cutting and continuing

Most commercial gateways can check each step an agent loop passes through, but when they find instructions injected into a tool's output they stop the agent rather than repair the output. They offer redaction only for sensitive data, not for injections.

| Product | Checks tool calls | Checks tool results | On injection | Default when the guard fails |
|---|---|---|---|---|
| Azure Foundry agents | Yes (preview) | Yes (preview, Microsoft-hosted tools only) | **Agent stops** | Undocumented |
| Azure APIM `llm-content-safety` | MCP and agent APIs | MCP and agent APIs | 403; stream silently cut | Undocumented |
| AWS Bedrock Converse | No | **No** (the prompt-attack filter skips `toolResult`) | Block or mask | n/a |
| AWS AgentCore Policy | Yes (`forbid`) | Yes (`suppressOutput`) | Deny or suppress | Default-deny (secondary source) |
| Google Model Armor | MCP `tools/call` request | MCP `tools/call` response | Error or empty response | Open (Vertex) |
| Portkey | MCP input | MCP output (regex-type checks only) | 446, or JSON-RPC error -32446 | Undocumented |
| Lakera Guard | Yes | Yes (tool results treated as untrusted) | The application decides; mask option | Undocumented |
| TrueFoundry / agentgateway | MCP before and after the tool runs | MCP before and after the tool runs | Validate, mutate or deny | Configurable; agentgateway fails closed by default |

Sources: [Foundry intervention points](https://learn.microsoft.com/en-us/azure/foundry/guardrails/intervention-points); [APIM](https://learn.microsoft.com/en-us/azure/api-management/llm-content-safety-policy); [Bedrock prompt attack filter](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-prompt-attack.html); [AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-guardrails-in-policies.html); [Model Armor MCP](https://docs.cloud.google.com/model-armor/model-armor-mcp-google-cloud-integration); [Model Armor and Vertex](https://docs.cloud.google.com/model-armor/model-armor-vertex-integration); [Portkey MCP](https://portkey.ai/docs/aigw/product/mcp-gateway/guardrails); [Lakera](https://docs.lakera.ai/docs/api/screening-roles); [TrueFoundry](https://truefoundry.com/docs/ai-gateway/guardrails-overview); [agentgateway](https://agentgateway.dev/docs/standalone/main/documentation/mcp/guardrails/about/).

Microsoft's Foundry docs state the halt directly: when a tool response contains an indirect attack, "the agent stops operating immediately" ([Foundry](https://learn.microsoft.com/en-us/azure/foundry/guardrails/intervention-points)). Lakera's model is the closest to how a gateway sees traffic. It screens the last interaction at every step of the loop, uses the full history only as context, and treats tool results as untrusted ([Lakera](https://docs.lakera.ai/docs/api/screening-roles)).

The model labs' agent-security guidance is more graduated than the products, matching the response to where the detection happens. For **malicious content in a tool result**, the guidance is to neutralise it and continue. Anthropic's developer docs say to replace flagged output with "an error or a stripped summary" and to consider telling the user ([Claude Docs](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)). Claude Code's auto mode keeps flagged output but adds a warning telling the agent to "anchor on what the user actually asked for" ([Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)). Google's Gemini defences "filter out harmful data containing malicious instructions… retaining only safe content" ([Google](https://blog.google/security/mitigating-prompt-injection-attacks/)), and AgentDojo's reference detector replaces flagged output with an omission notice by default ([AgentDojo](https://raw.githubusercontent.com/ethz-spylab/agentdojo/main/src/agentdojo/agent_pipeline/pi_detector.py)). For an **unsafe tool call**, the guidance is to deny that call and tell the model so it can look for a safer path: OpenAI's Agents SDK offers `reject_content` for this ([OpenAI Agents SDK](https://openai.github.io/openai-agents-python/guardrails/)), and Claude Code returns the denial as a tool result and escalates to the human after **3 consecutive or 20 total denials**. A **malicious user request** gets the turn refused, and halting the whole run is reserved for confirmed compromise. OWASP's new Agent Control Standard (v0.1, September 2026) gives this a common interface, with hooks at "tool call request" and "tool call result" that each return **allow, deny or modify** ([CSA note](https://labs.cloudsecurityalliance.org/research/csa-research-note-owasp-genai-top10-2026-agent-control-stand/)).

The research behind this guidance favours repairing over halting, with a strong caveat. **Halting costs all utility under attack**: in the MELON study on AgentDojo, a public benchmark of agents under prompt-injection attack, an LLM detector that ends the run on detection kept 81% of benign tasks but completed **0% under attack**, and a DeBERTa detector fell to 38% even on benign tasks ([MELON](https://arxiv.org/html/2502.05174v3)). **Repairing keeps most of it**: sanitisers that strip only the injection report attack success below 1% with little utility loss ([PromptArmor](https://arxiv.org/html/2507.15219v1); [firewalls paper](https://arxiv.org/abs/2510.05244)), and design-level isolation (CaMeL) costs about 7 points of utility, 77% against 84% undefended ([CaMeL](https://arxiv.org/abs/2503.18813)). But **the benchmarks are weak**: "The Attacker Moves Second" broke 12 published defences with attack success "above 90% for most" ([Nasr et al.](https://arxiv.org/abs/2510.09023)), and the firewalls paper itself says these benchmarks use weak, non-adaptive attacks. The repair numbers are therefore upper bounds. Microsoft draws the practical conclusion: a probabilistic detector "may not prevent or detect every instance", so guarantees have to come from deterministic controls such as egress blocks, least privilege and human approval ([MSRC](https://www.microsoft.com/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)).

**There is no standard for fail-open versus fail-closed.**

| Fails open by default | Fails closed by default |
|---|---|
| OpenAI's guardrails library ([OpenAI Guardrails](https://guardrails.openai.com/docs/quickstart)) | Claude Code auto mode |
| LiteLLM's LLM-as-a-judge guardrail | The OWASP agent cheat sheet ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)) |
| Model Armor on Vertex | agentgateway |
| | Cloudflare, when any category is set to block ([Cloudflare](https://developers.cloudflare.com/ai-gateway/features/guardrails/usage-considerations/)) |

A defensible split, which is a synthesis rather than any one source's prescription, is to fail closed on actions that change things or send data out, and to fail open with alerting on read-only screening, where an outage would otherwise stop all agent traffic.

## agentic-security follows the evidence on Chat Completions, less so elsewhere

Most of what `agentic-security` relies on is standard LiteLLM. Four pieces depend on LiteLLM internals, meaning undocumented behaviour that an upgrade could break: the in-place rewrite of a blocked reply, the streaming buffer flag, the `llm_router` module global, and the metadata convention that charges judge calls to the caller's key. Everything that makes decisions is our code: the window, the judge prompt and scoring, hedging, the deadline, fail-open, and the surgical cuts.

| Aspect | LiteLLM status | Our choice | Against the evidence |
|---|---|---|---|
| Hooks `pre_call` + `post_call`, no `during_call` | Standard | Ours: avoids the $0 billing we measured for blocks during `during_call` ([placement](../guardrail-placement.md)) | **Follows.** LiteLLM's Gray Swan page also warns against `during_call` for blocking |
| `apply_guardrail` override | Standard | [agentic_security.py#L329](../../deploy/agentic-security/agentic_security.py#L329) | **Follows.** Caveat: the proxy uses the unified path only if the class itself defines the method, so a subclass must redefine it |
| Pre-call screening of every tool result in a 10-message window | Data is standard; the window is ours | One judge call per request | **Follows** the Lakera and openai-guardrails pattern (that library's injection check defaults to 10 turns). **Gap:** results that scroll out of the window are not re-cut |
| Post-call check only when the reply has tool calls | LiteLLM runs `post_call` on every reply; the skip is ours | [#L381](../../deploy/agentic-security/agentic_security.py#L381) | **Follows** "check every tool call before it runs". Final text replies are unchecked, a residual risk the repo already documents |
| Withholding by returning a new `structured_messages` | Standard write-back | Surgical cut of injected lines (ours) | **Ahead of products, matches lab guidance.** No signal tells the client that input was changed |
| 200 refusal via `raise_passthrough_exception` | Built in, undocumented | Pre-call blocks and streamed blocks | **Follows** the provider and framework convergence |
| In-place post-call rewrite (`content_filter`, tool calls stripped) | **Internal** | Keeps the generated reply billed ([chargeback](../chargeback.md)) | **Follows** on Chat Completions. Anthropic and Responses replies fall back to the passthrough |
| `streaming_buffer_until_moderated = True` | **Internal** for custom guardrails; recommended on LiteLLM's OWASP page | [#L322](../../deploy/agentic-security/agentic_security.py#L322) | **Follows.** Costs time to first token on every streamed reply |
| Fail-open with a 10-second deadline | Ours; matches LiteLLM's own judge | [#L333-L341](../../deploy/agentic-security/agentic_security.py#L333-L341) | **Common and defensible.** Gaps: provider safety blocks become fail-opens, they are invisible in telemetry, and there is no per-hook split |
| Judge calls through the router, charged to the caller's key | **Internal** convention | Charges every judge call to the calling key and team ([chargeback](../chargeback.md)) | **Beyond LiteLLM**, which keeps vendor guardrail costs out of key and team spend entirely |
| Refusal reason kept out of the response | Ours | The reason goes only to the gateway log | **Follows** Kong and Lakera: no oracle for attackers |
| MCP hooks | Available | Not used | **Gap** if LiteLLM itself runs MCP tools |

The withholding design is where we are furthest ahead. The repo measured it against refusing the turn on AgentDojo and AgentThreatBench (ATB), another public benchmark, with a gpt-6-luna agent ([agentic-security.md](../agentic-security.md)):

| Arm | Task success under attack | Benign task success | ATB task success |
|---|---|---|---|
| No guardrail | 73% | 78% | 79% |
| cyber-guard (refuses the turn) | 6% | 61% | 12% |
| **agentic-security (surgical withholding)** | **56%** | 70% | **46%** |

**The 8-point benign cost (78% to 70%) is the price**, and it comes mostly from instructions the user delegated ("do the tasks on my TODO list") that look like injections. Surgical cutting matters because in 76 of 77 tasks that failed under whole-result withholding, the withheld result was the one the task needed: AgentDojo hides the attack inside the bill, email or file the task depends on. The locate step that finds the injected lines kept a median of 87% of the text and added about 1 s at the median. This matches what Google, Anthropic's developer docs and AgentDojo's default detector do, and goes beyond Azure Foundry, Portkey and Model Armor, which halt the agent or return an error.

Two caveats limit how far the protection numbers stretch. **The gpt-6-luna agent resisted every AgentDojo attack even without a guard**, so the evidence that the guard prevents attacks rests on a small run with the weaker Gemma 4 model (12 AgentDojo samples, all banking), where attack success fell from 42% to 0%. And **the repo's claim that "200 vs 400 made no difference" compared a native 200 with a 400 that the eval shim had already converted into a 200 refusal** ([README](../../README.md); [shim](../../evals/agent/shim.py)), so no agent in that run ever saw a raw 400. The case for 200 rests on the external evidence above and on measured billing (raising records a post-call block as a $0 failure), not on the repo's task-completion data.

There are three deviations from best practice. **A blocked tool call ends the whole turn.** Our post-call block refuses the entire reply, rather than denying the one tool call and telling the model, as Claude Code and OpenAI's `reject_content` do. A gateway cannot easily do otherwise, because the client runs the tools and only the client can hand a tool result back; LiteLLM's one first-party way around this, the Agentic Loop Hook, reruns the model server-side but does not support streaming Chat Completions and adds an inference call and a judge call per denial ([Agentic Loop Hook](https://docs.litellm.ai/docs/proxy/agentic_loop_hook)). In practice our design hands the decision to the human on the first denial, the conservative end of the range, acceptable at the measured 1.2% legitimate-block rate on the tool-call dev set.

**Only Chat Completions works fully.** On `/v1/messages` and `/v1/responses`, the tool-call judge sees little or none of the conversation, because it builds context from `request_data["messages"]` ([#L383](../../deploy/agentic-security/agentic_security.py#L383)), which skips Anthropic tool blocks and the top-level system prompt and does not exist for Responses requests. That matters because the action check's measured 81% catch rate on intent deviation depends on seeing what the user asked ([placement](../guardrail-placement.md)). The in-place rewrite also does not apply there, since it only understands Chat Completions replies, so post-call blocks fall back to the passthrough, with `end_turn` on Anthropic, the malformed output item on Responses, and probably the $0 failure record the repo measured for raised post-call blocks on chat.

**Our action judge sees the tool results.** Claude Code strips tool output from its action classifier and calls that "the primary prompt-injection defense" ([Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)), while Codex's reviewer includes tool outputs labelled as untrusted ([OpenAI](https://alignment.openai.com/auto-review/)). Our post-call judge follows Codex, seeing tool results clipped to 1,500 characters and JSON-escaped. That is defensible, but untested against the alternative.

**The lab's `LabGuardrail` is the same LiteLLM pattern with four production problems** ([litellm_guardrail.py](../../src/guardlab/litellm_guardrail.py)). Its `on_block: error` returns a 400 containing the judge's reason, which both leaks an oracle and ends agent runs. It merges client-supplied `metadata`, so a caller could charge its judge calls to another key. It has no deadline by default. And it keeps an in-process verdict cache, which breaks the no-state constraint. It should stay in the lab.

The top four should land before the guard enforces on enterprise traffic. Each fits the constraint of one Python file plus config, with no cache and no new infrastructure.

The first change carries the most risk per line of code. **The guard fails open on exactly the content most likely to be dangerous**, because a judge prompt that contains real exploit material is the one a provider's cyber classifier is most likely to refuse, and **the fix is small**: recognise the policy error codes and empty `content_filter` replies, treat them as a top digit, and pass a hashed caller ID as `safety_identifier` after checking that LiteLLM forwards the parameter. How often this happens is unknown; the clean reference run had zero fail-opens, but AgentDojo's injections are weak by the firewalls paper's account. The second and third changes protect the clients this enterprise most likely runs, since Claude Code speaks Anthropic Messages and Codex speaks the Responses API, while every chargeback check and agent evaluation in the repo used Chat Completions only. The fourth matters because fail-open is our default, and a fail-open that LiteLLM records as "success" can quietly become the gateway's steady state during a rate-limit storm.

Several mechanisms are deliberately **not** recommended:

| Not recommended | Reason |
|---|---|
| `during_call` | A block cancels the model call mid-flight, which we measured recorded as $0 |
| `only_scan_new_messages` | Needs a cache |
| The Agentic Loop Hook rerun | Partial endpoint support; an extra inference call and judge call per denial |
| `on_block: error` in production | Aborts agent runs and leaks the judge's reason |
| Setting `message.refusal` | The Agents SDK raises on it |
| Switching Anthropic replies to `stop_reason: "refusal"` | Claude Code shows it as an "API Error" and users report the session staying blocked; switch only after testing Claude Code against it |

## Conclusion

The format question is largely settled: a 200 refusal with explanatory text and a recognisable stop signal is what providers, frameworks and LiteLLM's own built-ins are converging on, and `agentic-security` already emits it. The open risk lies in the paths nobody has exercised (non-chat endpoints, judge-provider refusals, turns longer than the window, MCP tools that LiteLLM runs itself), and each one fails quietly in the attacker's favour. The guard's weakest point is therefore not detection accuracy, which is on par with the lab's best at F1 0.93 on held-out sets ([agentic-security.md](../agentic-security.md)), but how it behaves when something around it breaks, which makes the next work reliability engineering more than judge tuning.

Surgical withholding is a genuine differentiator, since no major gateway product offers "cut the injection and continue". The benchmarks that show its value use non-adaptive attacks, though, and adaptive attacks have broken nearly every published detector. Deploy it the way Microsoft, Google and LiteLLM all advise: as the layer that keeps agents productive, behind deterministic controls (tool permissions, egress limits, human approval for irreversible actions) that LiteLLM Enterprise can already enforce with configuration alone.
